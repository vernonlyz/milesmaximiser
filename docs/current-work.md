### MCC-first engine (Level 2) — 2026-08-25 [tag: v9.0-mcc-engine]
The recommendation engine now consumes MCC eligibility (previously informational only). Two layers:
- **Layer 1 — MCC (when confirmed):** an MCC is trusted to gate when it's typed, or the vendor supplying it is tagged `confirmed`/`likely` (only `unverified` is distrusted). `resolveMccGate(card, mcc, overrides, channel, date)` → `'base'` (demote to base — blacklist hit, not whitelisted, wrong channel, not a chosen category), `'bonus'` (promote a **whitelist/hybrid** card to its **channel-applicable** bonus rate even when the picked category has no rate row), or `null` (defer).
- **Layer 2 — category (fallback):** no/unconfirmed MCC, no card model, an eligible **blacklist** card (earns its wildcard/flat rate via the category path — deliberately not promoted, so flat cards don't pick up their FCY rate), or an indecisive verdict.
- **Rate:** `getEffectiveForCard` gains an `mccGate` arg. `'base'` → base on the whole amount; `'bonus'` → the card's headline channel-applicable bonus rate with a cap fallback (channel → picked-category → pool → any non-channel cap); `null` → unchanged. Channel + chosen-category are enforced by the resolver, so DBS Woman's World online-only, Preferred's caps, Visa Sig min-spend, etc. are untouched.
- **Caps (phase 2):** `buildPeriodSpending` takes an optional `baseMpdByCard`; a bonus cap then counts a transaction by whether it **earned bonus** (`effective_mpd > base`) rather than by category — so Revolution's pool and DBS/Citi's online channel caps count MCC-eligible spend (a promoted MCC under a non-bonus category counts; a demoted one doesn't). Omitted → category counting (backward compatible; existing tests hold). Relies on `effective_mpd` being stored on miles transactions (always is).
- **Threading:** an optional `MccContext { code, confirmed, rows, categories }` on `calcMiles`/`recommendCards`; the log form + Recommend derive `confirmed` from typed-vs-vendor-confidence and pass `cardMccEligibility` + `categories`. Recurring-occurrence generation stays on Layer 2 for now.
- **Tests:** engine suite grew to **38** (gate demote/promote, blacklist-no-promote, unconfirmed fallback, no-model ignore, channel-rule guard, MCC-aware pool/channel cap counting, per-category cap attribution, no-method channel sweep, backward-compat).
- **UX:** the log-form Recommendation widget is expandable (top 3 → "Show all N cards").

**MCC engine — closing the loop (v9.1, 2026-08-26):**
- **Recompute miles (Admin, dry-run → apply):** re-runs `calcMiles` (with the MCC gate) over all the user's miles transactions oldest-first (so caps fill cumulatively and MCC-aware counting reads freshly-recomputed priors); manual overrides + non-miles rows untouched. Dry-run reports "N txns · X changed · net Δ miles" before writing. Use this once to align pre-v9.0 history.
- **Recurring occurrences use the MCC gate** — `computeEarn` builds an `MccContext` from the favourite's stored MCC (+ vendor confidence), so generated future charges earn what a manual log would.
- **Per-category cap attribution** — `MccContext.categoryId` (from `mcc_catalogue.default_category_id`); `getEffectiveForCard` prefers the MCC's mapped-category cap when promoting, so Preferred's $600 online-shopping / Lady's $750 draw correctly instead of the pool/first-cap fallback.
- **No-method cap-aware channel sweep** — `bestChannelEff` evaluates contactless + online (each with its caps + gate) when no method is chosen and keeps the best, so a channel-split card can't show full bonus while the method you'd use is capped; `CardRecommendation.bestChannel` names the winner.
- **"Why" labels in the log form** — one prioritised line: cap-reached (`<category> cap reached · <method> — earns base`), partial (`S$X left in <category> cap`), MCC-demoted (`MCC not eligible → base rate`), best-via (`best via <method>`), or MCC-promoted (`bonus via MCC`).
